# Краткое описание проекта ARIA

## Проблема

Владельцу магазина приходится сопоставлять продажи, остатки, сроки и цены в разных инструментах. Разрозненные данные затрудняют своевременное решение о пополнении, скидке или передаче пригодного излишка.

## Цель

Объединить учёт и поддержку решений в одной платформе ARIA, сохранив проверку ограничений, права пользователей и прослеживаемость операций.

## Пользователи

Владельцы и сотрудники магазинов используют административную панель. Покупатели работают с демонстрационной витриной. Проверенные социальные организации участвуют в согласованной передаче товаров.

## Основные функции

Каталог, партии, заказы, корзина, внутренняя касса, закупочные черновики, ценовые рекомендации, импорт цен конкурентов, социальные предложения и подключения магазинов. WooCommerce читает внешний каталог и заказы в отдельные снимки; запись во внешний магазин не включена.

## Взаимодействие Frontend и Backend

HTML, CSS и JavaScript формируют страницы. Fetch API передаёт запросы REST в Spring Boot. Контроллеры проверяют доступ и входные данные, сервисы выполняют бизнес-операции, JPA сохраняет состояние в PostgreSQL.

## Особенность решения

Java рассчитывает допустимые сценарии, а нейросеть может участвовать в выборе или объяснении. Ответ модели проходит серверную проверку. Источники AI и автоматического расчёта различаются; нейросеть не исполняет произвольный SQL и не меняет цены напрямую.

## Практическая значимость

Единая история партий, цен и операций помогает проверять причины управленческих решений. Снижение потерь или рост прибыли в реальном магазине в этой работе не измерялись.

## Логика работы

Карточка товара → приёмка партии → анализ доступных данных → рекомендация → подтверждение либо разрешённое действие в границах → учёт продажи или социальной выдачи. Демонстрационная витрина использует то же бизнес-ядро, но её учебные значения не являются рыночными наблюдениями.
