# Продолжение регистрации и ARIA 3.0

Сначала `git status`, HEAD, удалённая `codex/production-foundation`. Не сбрасывать изменения. База до этого этапа — `822e2cd`; не повторять Smart Pricing, WooCommerce, RU/EN и предыдущие исправления.

## Готовый этап 1а

`CompanySignupService/Controller`, `CompanyRegistrationRequest`, V33. Отдельная БД/роль `aria_registration_local`, процесс 8088, binding `aria-registration`. UI: `/company-start.html`, `/company-requests.html`; вход и коды только в игнорируемой `data/onboarding`. Мобильный RU/EN, согласия, CAPTCHA/лимиты, SHA-256 кода, идемпотентный повтор после потерянного ответа, ручная проверка и версии, поиск/фильтр, история, настоящее сохранение после рестарта. Полный PostgreSQL-прогон 259, отдельно UI/E2E. Публичный `/api/auth/capabilities` сохраняет два прежних флага, новый сервис имеет собственный `/api/company-signup/capabilities`.

У заявки пока четыре состояния: SUBMITTED, IN_REVIEW, VERIFIED, REJECTED. **workspaceReady/accountCreated всегда false** — это осознанная защита, не готовая регистрация компании. Два проверенных учебных обращения и одна закрытая учебная проверка формы; не представлять их реальными клиентами.

## Следующий завершённый этап 1б

1. Сохранить отдельный процесс/БД для компаний. Не давать веб-приложению административный доступ к PostgreSQL/Render и не создавать платные ресурсы. Подготовку нового окружения выполняет оператор, сначала только новая локальная учебная компания.
2. После VERIFIED оператор получает защищённую спецификацию для новой компании: request ID, будущая binding, контакт владельца, хеш кода заявки. Сам код ему не раскрывается. Отдельный секрет проверки хранить через IntegrationVault; спецификацию/ключи не коммитить и не показывать на скриншотах.
3. Новое пустое окружение должно подтвердить привязку, действительную БД и подготовленную учётную запись владельца. Проверять ответ работающего сервера, не принимать просто введённый URL или checkbox за готовность. Сетевую проверку выполнять вне транзакции с повторной проверкой версии/состояния перед сохранением.
4. Разрешать только HTTPS и операторский список доменов; запрет SSRF/redirects. Для локального E2E — узкое исключение только точного loopback-адреса нового учебного процесса/БД, не общее разрешение локальных адресов в production.
5. Добавить одноразовую активацию владельцем по сохранённому коду и выбор собственного пароля (существующая политика AuthService). Код не помещать в query/логи. Состояние использования сохранять; повтор/подмена request ID/чужая компания/устаревшее решение должны отклоняться. До активации не выдавать бизнес-токены нового кабинета.
6. Запретить такое присоединение к существующей заполненной компании и повторную привязку чужого процесса. OrganizationBoundary/JWT issuer/version и все прежние ограничения сохранить.
7. UI: проверенная заявка → ожидание реальной подготовки → кнопка активации только после проверки работающего окружения → пароль → вход в новый пустой кабинет → «Мои магазины». Реальный локальный E2E двумя процессами и базами, отрицательные сценарии, перезапуск, тесты, commit/push/CI.
