# ARIA B2B — карта перехода, 30.10.2026

## Карта существующей системы

Java/Spring Boot + JPA, PostgreSQL/Flyway V1–V18, HTML/JS. AppUser и JWT/роль ADMIN защищают административные API. Product, InventoryLot, Order/OrderItem, POS, Purchase, PricingDecision, SocialProposal и журналы используют одну базу. Smart Pricing — authority для ограничений; OpenRouter выбирает проверяемый сценарий. ManagerTask/ManagerExecution и singleton ManagerStore/настройки сохраняются в БД. Есть собственные исполнители, кэши/лимиты и служебные потоки. Публичная витрина читает тот же каталог.

## Решение для первого пилота: silo tenancy

Одна Organization → одна отдельная БД **и отдельный процесс**, отдельные секреты, upload-directory и URL. Это multi-tenant продукт с изоляцией развёртываний, не общий runtime с выбором tenant заголовком. ConnectedStore и ExternalIntegration принадлежат единственной организации базы. Все прежние запросы и фоновые операции получают tenant scope границей процесса/БД. Не нужно переписывать рабочие сервисы или полагаться на забываемый `WHERE organization_id`.

Изоляция лишь баз при общем процессе недостаточна: старые singleton-сервисы, фоновые очереди, AI-бюджеты, security context и uploads могли бы смешаться. Header/URL из браузера не должен выбирать JDBC URL. Общая схема с RLS потребует отдельного полного перехода всех сущностей, native queries, аутентификации и контекста исполнителей; её сейчас не выдаём за реализованную.

Недостаток silo: отдельные процессы расходуют больше ресурсов. Для бесплатного пилота проверяем два локальных экземпляра; бесплатное облако не обещает неограниченное число компаний. Self-service регистрацию нельзя включать, пока нет безопасного provisioning и подтверждённой квоты. Центральный control plane/биллинг — следующий этап, без платёжного подключения.

## Риски и границы

- Organization в SaaS отличается от благотворительного получателя с ролью ORG; их нельзя смешивать.
- Внешний заказ не означает локальную отгрузку. Нельзя автоматически списать местный склад при импорте и ещё раз при статусе.
- WooCommerce stock_quantity не даёт партии, себестоимость или срок. Не создавать подтверждённые партии из этих полей; для внешних снимков нужны отдельные mapping/snapshot/inbox.
- Начальная интеграция read-only. Внешние цены запрещены до проверенных прав, свежего снимка, разрешения владельца и E2E. Webhook принимается только после проверки HMAC исходного тела; нужна постоянная inbox/dedup, а не обработка до подтверждения приёма.
- Все credentials — серверное шифрование с отдельным ключом и отзывом; не URL/query/localStorage/log. Адреса connector требуют защиты SSRF, запрета редиректов и контроля egress.
- Изоляция deployment требует разных DB-login, JWT secret, upload-path и origin. Дополнительный issuer/organization claim отклоняет токен другой компании даже при ошибочно одинаковом signing key.
- Существующая демо-база получает binding `demo`; копирование этой базы не регистрирует новую компанию. Binding чужой базы должен остановить запуск.

## Порядок этапов

1. Binding организации и JWT; модель Organization → ConnectedStore → ExternalIntegration, ограничение одной организации в silo; проверка двух отдельных БД/токенов, старые regression tests.
2. Provisioning пустой компании с OWNER/membership, отдельными DB-правами и файлами. Read-only WooCommerce, encrypted credentials, mapping/snapshots, sync journal, signed inbox, retries/conflicts. Shopify/Kaspi — только интерфейсы до реального доступа.
3. Проверенные внешние снимки → scoped AI-анализ; неполнота данных блокирует необоснованные действия. Получить действительный тестовый WooCommerce (локальный WordPress/WooCommerce тоже подходит), не подменять моками.
4. Отдельные проверки внешней записи и reconciliation, затем явное разрешение владельца. Unknown outcome после сетевого сбоя требует чтения внешнего состояния до повтора.
5. Opt-in ARIA Impact, tenant roles/exports/deletion/backup, мастер подключения и чёрно-белая B2B-навигация; витрина остаётся демо.
6. Реальный E2E двух магазинов, сбои/webhooks/отзыв доступа и бесплатный staging. Только после этого коммерческий пилот. Main/production/платные подключения — отдельно разрешаемые действия.

Официальные источники: [WooCommerce REST API](https://woocommerce.github.io/woocommerce-rest-api-docs/), [webhooks](https://developer.woocommerce.com/docs/best-practices/urls-and-routing/webhooks/). Mock contract test не считается проверкой настоящего магазина.

## Реализованная граница первого этапа

V19 добавляет saas_organization, connected_stores, external_integrations. Legacy-данные остаются на месте в demo; пустые ConnectedStore не означают подключённый WooCommerce. `OrganizationBoundary` проверяет фиксированную конфигурацию `ARIA_ORGANIZATION_KEY` против единственной записи БД до готовности приложения. Другая привязка останавливает запуск, а не переименовывает чужую компанию. Для свежего silo нужна отдельная контролируемая provisioning-процедура; публичная регистрация ещё выключена.

JWT требует issuer `aria:<key>` и organization claim. Старые токены без claim отзываются этим изменением: потребуется повторный вход; пароли/аккаунты сохраняются. Один и тот же email допустим в разных БД. GET `/api/admin/control/organization` доступен только ADMIN, возвращает текущую привязку/статус и несекретные сведения магазинов. Пользовательский header не меняет организацию.

Для недемонстрационных binding все `/api/**`, кроме входа, требуют ADMIN. Публичный каталог, показатели Impact и клиентская регистрация там не открывают доступ к данным компании. Демонстрационная организация сохраняет существующую витрину/клиентские сценарии. Новая модель ролей/членства ещё нужна перед предоставлением доступа сотрудникам с ограниченными правами. `demo` зарезервирован для публичной демонстрации и не должен использоваться для компании пилота.

`StoreConnector` задаёт read-only интерфейс снимков/пагинации и явно проверяемых разрешений. Это **контракт, не готовый WooCommerce Connector**. HTTP-адаптер, секреты, импорт, webhook inbox и разрешённая внешняя запись ещё не реализованы. Названия Shopify/Kaspi в enum не означают соединение.

`impact_enabled` — пока подготовленное поле, не завершённый opt-in workflow: существующий социальный модуль сохранён. Компаниям пилота нельзя обещать применение этого переключателя до отдельной интеграции. Роли OWNER/STAFF/membership, тарифы/usage, экспорт/удаление и B2B-мастер — следующие этапы; существующая ADMIN-роль их не заменяет.

Проверка: `.\mvnw.cmd test`; отдельно `powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/b2b-isolation-e2e.ps1` (собрать JAR заранее). E2E допускает только собственный локальный preview PostgreSQL 55434, создаёт две новые пустые базы/ограниченные роли, мигрирует V1–V19, запускает два настоящих приложения 8096/8097, проверяет одинаковый SKU/email, чужие JWT и запрет межбазового входа. Секреты остаются в окружении дочерних процессов, журналы/отчёт — в исключённом data/b2b-isolation-*. Процессы завершаются, данные теста сохраняются. Это E2E изоляции ARIA, **не E2E WooCommerce**.

## Подтверждённые результаты этого этапа

30.10.2026: сборка package и **139 тестов** прошли, failures/errors/skipped=0 (включая прежние 59 интеграционных сценариев). Пять новых проверок: чужой issuer при одинаковых signing key/email; старый токен без scope; повторная инициализация demo; запрет переименования скопированной demo; обязательное provisioning и запрет второй организации.

Финальный настоящий E2E двух процессов и PostgreSQL прошёл: `data/b2b-isolation-1793303954/report.json`, passed=true. Миграции V1–V19/validate, одинаковые SKU с разными именами, чужие токены для products/manager/organization → 401, анонимный доступ к бизнес-каталогу/Impact/организации → 401, чужой DB-login → PostgreSQL permission denied. Подтверждено при намеренно одинаковом JWT signing key. Тестовые процессы завершены; production не использовался. JAR для теста копируется отдельно, поэтому будущая сборка не блокируется работающим тестовым процессом.

Не проверено и не объявлено готовым: настоящий WooCommerce, внешняя запись/синхронизация/webhooks, SaaS-роли/онбординг, opt-in Impact для компаний, новый B2B-интерфейс и облачный пилот. Тестового WooCommerce у владельца пока нет; на машине не обнаружены Docker/PHP, позволяющие сразу поднять WordPress. Следующий внешний этап требует настоящего отдельного тестового магазина или подготовленного локального окружения. Этот фундамент нельзя продавать как завершённую SaaS-платформу.
