# Отдельный staging ARIA 4.0

Основа автономного цикла — `d5d1143`, [CI успешен](https://github.com/2berCOOL3znikk/shop-aria-deploy/actions/runs/43367191157). Новая среда готовится из `codex/production-foundation`; основной `shop-aria` остаётся на `main` без изменений.

## Изоляция

Создан отдельный проект Neon **ARIA 4 Staging**, `dawn-dew-85661116`, в уже существующей организации с планом Free. Новая пустая БД `aria_staging`, отдельная роль `aria_staging_owner`, привязка `aria-v4-staging`. Это не ветка с копией рабочих строк: ни таблицы production, ни её контакты/ключи не читались и не переносились. Миграции V1–V35 применены в новой базе, владелец создан, привязка проверена локальным запуском.

Профиль `staging` дополнительно проверяет **до запуска Flyway** точный сервер новой БД, имя базы, роль и компанию. Случайная подстановка другого подключения приводит к отказу до миграций. Существующие защитные проверки production сохраняются.

В новой компании нет товаров, магазинов, продаж, ценовых действий или внешних AI-согласий. OpenRouter-ключ и учебная история WooCommerce сюда не копируются. [Подтверждённый автономный сценарий и его цена](AUTONOMY_RU.md) остаются в прежней учебной среде.

## Подготовленный сервис Render

Параметры для нового сервиса зафиксированы в `scripts/staging/service-spec.json`: отдельное имя `aria-v4-staging-2ber`, план `free`, Frankfurt, Docker, рабочая ветка и **выключенный автоматический deploy**. Существующий `render.yaml` и сервис production не меняются. Секреты поступают только из защищённого `data/staging/config.json` в переменные **нового** сервиса, не в репозиторий.

Публичный URL будет считаться готовым только после состояния Render `live`, совпадения сборки и браузерной проверки входа. До этого проверенный адрес на этом ПК: [локальный staging](http://127.0.0.1:8091/start.html). Результат подготовки: [проверка новой среды](evidence/staging/local-result.json), [главная](evidence/staging/local-workspace-1440.png).

## Вход и проверки

Email владельца — ранее указанный владельцем проекта. Отдельный случайный начальный пароль находится только в `backend/data/staging/access.txt`; не пересылайте этот файл. Авторизация новой среды не использует сеансы других компаний.

На главной видна подпись **«Тестовая онлайн-версия»**, настоящие нули и следующий шаг «Подключить магазин». Для внешнего магазина нужны его собственные WooCommerce credentials и разрешённый домен на сервере. Без них коммерческое подключение не считается выполненным.

`scripts/staging/start-local.ps1` запускает только этот известный staging на 8091, без пересоздания существующей компании. `scripts/staging/smoke.cjs` проверяет реальный вход, пустую главную, магазины и AI-центр на 390/1440 px; произвольные и production URL не принимает. Для новых операций скрипт ничего не создаёт.

Прошли 8 целевых проверок прав/маркировки/защитной конфигурации и 8 браузерных проверок локального staging с облачной БД. Полный набор — CI; локально его не повторяли.

## Бесплатные ограничения

Тарифы не повышались, платные worker/cron/диски/БД не создаются. Render Free засыпает без входящих запросов; в это время автономных действий нет. Бесплатные часы и сборочные квоты Render общие для рабочего пространства: постоянно активный staging не обещается и искусственных пингов нет. Файлы внутри контейнера временные; постоянные бизнес-данные находятся в отдельном Neon. [Ограничения Render Free](https://render.com/docs/free), [тарифы Neon](https://neon.com/pricing).

Для выпуска production сначала проверить совместимость миграций/восстановление на отдельной копии, целевые сценарии и согласия, зафиксировать зелёный CI и проверенный staging, затем получить отдельное разрешение на backup, миграции и переключение рабочего сервиса. Текущий staging не является таким разрешением.
