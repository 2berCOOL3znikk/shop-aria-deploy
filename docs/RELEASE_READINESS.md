# ARIA: проверка перед публикацией — 29 октября 2026

Ветка: `codex/production-foundation`. Основной Render, main и production-база не изменялись. Проверки выполнены на отдельных локальных PostgreSQL; пользовательский preview использует собственный кластер и базу в `data/preview`.

## Как посмотреть

[Пошаговая инструкция запуска и проверки](PREVIEW_GUIDE.md). Витрина запущенного стенда: <http://127.0.0.1:8084/index.html>, управление: <http://127.0.0.1:8084/control.html>. Начальные данные входа — в локальном `data/preview/access.txt`, не в репозитории. Все проверочные товары, аккаунты, цены конкурентов и документы явно синтетические. Они не предназначены для переноса в магазин.

## Что проверяется

- Вход владельца и покупателя, регистрация с одноразовой капчей, серверное разграничение ADMIN/USER/ORG, отсутствие доступа покупателя/гостя к административным API и отчётам. Смена пароля и отзыв старых токенов покрыты серверными интеграционными тестами.
- Создание/изменение карточки, приёмка/исправление партии, фото в PostgreSQL, поставщики и запрет удаления связанной истории, списание и архивирование.
- Реальный внешний AI в панели, Java-ограничения, ручное подтверждение скидки, цена в клиентской карточке, избранное, количество/адрес в корзине, оформление, уменьшение остатка, отправка и доставка.
- Организация проходит проверку; условия приёма подтверждаются отдельно. Черновик не резервирует товар. Подтверждение создаёт резерв; фактическая выдача отдельно списывает остаток и появляется в отчёте.
- CSV конкурентов действительно читается из файла и импортируется с идентификацией товара; тестовые котировки не выдаются за наблюдения реального рынка. Помощник использует каталог стенда, бюджет и повторную проверку наличия.
- Ручной калькулятор/снятие скидки, правила категории/сброс, откат Smart Pricing, настройки автопилота/экстренная остановка, журнал; ошибки одного раздела не блокируют обзор.
- Поддержка: ошибка капчи/повтор, сохранение сообщения, просмотр и обработка администратором. Поиск/сортировка каталога, отсутствие результатов, темы и переключение языков.
- Все разделы управления, старые анализы/история и основные публичные страницы: desktop 1440 px и mobile 390 px, внутренние ссылки, загрузка изображений и ошибки JavaScript. Неверный ID товара показывает понятное отсутствие карточки.

Результаты с точными счётчиками текущего прогона находятся ниже; машинные браузерные отчёты сохраняются в `target/e2e/report.json` и `maintenance-report.json`. Проверка ширины и ссылок не доказывает все возможные состояния интерфейса или доступность для всех ассистивных технологий.

## Исправления аудита

1. Корзина не удаляет строку до успешного ответа сервера, показывает причину отказа оформления, не допускает одновременных повторных операций и сохраняет введённый адрес при изменении количества. Заполненная корзина переносится на узком экране. Убран фиктивный предзаполненный адрес.
2. Профиль не показывает успешное сохранение при 4xx/5xx, сохраняет заполненные поля при ошибке. Сервер проверяет длины до записи в PostgreSQL. Неверные/пустые отзывы возвращают 400 вместо внутренних ошибок.
3. Старая `product-detail.html`, содержавшая Java-класс вместо HTML, переведена на действующую карточку с сохранением ID.
4. Общая форма админки блокирует повторную отправку во время сохранения.
5. Smart Pricing описан в инструкции как основной сценарный механизм. Старый ручной калькулятор сохранён и явно отделён от него.
6. Неподтверждённый адрес поддержки и вымышленные часы убраны; ссылки ведут к работающей форме. Сообщения уже существующего API доступны в админке. После ошибки капчи выдаётся новый пример без потери текста.
7. Страница конфиденциальности описывает фактическое постоянное хранение, доступ администратора и отдельные согласия OpenRouter; не обещает удаление базы при остановке.
8. Для социальной полки добавлен CSV именно подтверждённых фактических выдач со снимками названия/SKU/закупки и временем. Формулы в текстовых CSV-полях нейтрализуются также после ведущих пробелов.
9. Устранён воспроизведённый OpenRouter HTTP 400: `Reasoning is mandatory for this endpoint and cannot be disabled`. Запросы больше не запрещают reasoning, используют низкую интенсивность и исключают его из ответа. Тайм-ауты, строгая схема, проверка Java и нулевые ценовые ограничения сохранены. Основание: [OpenRouter reasoning](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens).
10. В Free-профиле устранён минутный опрос настроек AI, который мог держать Neon активным. Отключённое расписание не обращается к БД и явно обозначено в настройках.
11. Добавлен безопасный локальный запуск/остановка preview. Исправлено зависание Windows при наследовании потоков вывода PostgreSQL; версия Java проверяется с учётом особенностей stderr в Windows PowerShell. Собственная база защищена паролем, HTTP и PostgreSQL привязаны к loopback; случайные пароли исключены из Git.

## База, резервирование и инфраструктура

Проверены Flyway V1–V11 и Hibernate `validate` на чистой PostgreSQL. Проверена логическая копия заполненной синтетической базы: восстановление в другую базу, сравнение количества и содержимого всех 31 таблицы и последовательностей, включая фотографии, цены, заказы и историю. SHA256 проверяется до восстановления; исходная/непустая база и неверный digest отклоняются. Восстановление выполняется одной транзакцией, без `--clean`. До production эту же процедуру нужно повторить с отдельно разрешённой рабочей копией.

Файлы запуска и копирования: `Start-ARIA-Preview.cmd`, `Stop-ARIA-Preview.cmd`, `scripts/start-preview.ps1`, `scripts/stop-preview.ps1`, `scripts/backup-postgres.ps1`, `scripts/restore-postgres.ps1`. Установленная локальная PostgreSQL 18 используется только для проверки. В Neon сохранена PostgreSQL 17; фактический деплой на её main не выполнялся.

Профили `postgres,production,free`: без demo-seed/reset/H2 console, Flyway+validate, heap 256 MB, до трёх соединений, без постоянного диска Render, фото в PostgreSQL. `/actuator/health` проверяет процесс и не подтверждает доступность базы; бизнес-запрос проверяется отдельно. Blueprint/Dockerfile не требуют платных сервисов. Контейнер в этой проверке не запускался в Render: проверена работа приложения с теми же профилями и ограничением heap, а не реальный облачный деплой.

## Ограничения и что ещё нельзя обещать

- Render Free засыпает; постоянная доступность и выполнение фоновых заданий по настенным часам не гарантируются. Free-часы общие для workspace, отдельный онлайн-staging расходовал бы их вместе с основным сайтом. Бесплатные лимиты внешнего AI также ограничивают доступность. Никаких платных резервных моделей или автоматического upgrade.
- Оценки Smart Pricing — сценарии на доступной истории. На свежем каталоге модель вправе выбрать KEEP; в E2E ручные 5% не обозначаются как AI-рекомендация. Нет доказательства причинного роста продаж.
- Сохранены существующие ограничения: целые единицы, социальный резерв на весь SKU, ручная проверка пригодности и перевозки, выдача с отдельным подтверждением.
- Оплата, автоматическое письмо/доставка и восстановление пароля по email не подключены. Приём настоящих заказов требует утверждённых условий магазина, ответственного за обращения и резервные копии. Платёжные реквизиты не собираются.
- Защита от частых входов и запросов частично в памяти одного экземпляра. Эта проверка не заменяет независимый penetration test или нагрузочное испытание.
- Локальный preview не является публичным staging и доступен только при включённом компьютере. Русский — основной язык; новые административные тексты не полностью переведены на другие языки.

## Точный порядок безопасного production deploy

1. Зафиксировать проверенный commit рабочей ветки и получить отдельное разрешение владельца на резервную копию/публикацию/переключение. Пока не разрешено — main и рабочий сервис не изменять.
2. Сверить действующий Render, привязанную ветку, конфигурацию, состояние данных и оплату. Сохранить настройки для отката без вывода секретов в Git/чат. Отключение авто-деплоя также требует разрешения.
3. В согласованное окно прекратить изменения/заказы на старой версии. Сохранить разрешённую копию фактических данных. Старый H2 на Render эфемерен: перезапуск до выгрузки может потерять его. API snapshot не считается полноценной копией H2 — нужно отдельно сверить, какие поля, аккаунты, фото и связи реально выгружены.
4. Восстановить копию в отдельной PostgreSQL и проверить полноту данных, сроки, количество, суммы, фото и вход владельца. Не загружать синтетические данные preview в магазин. Если штатный перенос старого H2 не покрывает все связи, остановиться на этом шаге и подготовить проверяемый конвертер; не заявлять миграцию завершённой по одному JSON.
5. Проверить миграции V1–V11 и новую сборку на изолированной копии/ветке Neon. Использовать direct TLS connection для миграций и backup/restore; не применять их пробно к Neon main. Не переименовывать исторические миграции и не менять их checksum.
6. После отдельного разрешения опубликовать именно проверенный commit в разрешённую ветку деплоя. При переходе старого H2 на Neon сначала подготовить новый код без demo/reset, затем атомарно согласовать рабочую конфигурацию: `postgres,production,free`, правильный адрес БД, собственные секреты владельца/JWT, сохранение прочих переменных. Не запускать старый main против новой рабочей базы.
7. Явно сохранить Render **Free**, не создавать Render PostgreSQL/disks/workers. OpenRouter-ключ оставить серверным секретом, `openrouter/free`, нулевые цены; разрешения в новой базе по умолчанию выключены. RECOMMEND остаётся исходным режимом.
8. Дождаться успешного deploy/health и выполнить smoke на фактическом URL: вход, чтение БД, фото, отдельный проверочный заказ с контролируемой отменой, права, AI/ENGINE, социальная выдача только при реальном согласовании. Проверить перезапуск и сохранность, подтвердить резервное копирование. Затем открыть приём заказов.
9. При ошибке остановить изменения и сверить, успели ли появиться новые заказы. Откатывать код только к версии, совместимой с текущей схемой. Не переключать слепо на старую копию, теряя новые записи. Восстанавливать в отдельную базу, сохранить исходную и документировать расхождения; destructive down-migration не выполнять.

Актуальные ограничения инфраструктуры сверены с [Render Free](https://render.com/docs/free) и [порядком deploy](https://render.com/docs/deploys). Бесплатный вариант подготовлен для защиты и ограниченного пилота; он не даёт гарантий круглосуточного магазина.

- Blueprint JSON Schema и синтаксис всех клиентских JavaScript: **PASS**. Free-only, без Render databases/disks. Облачного deploy и запуска Docker-контейнера не было.
- Доказательства без секретов: [release-evidence-2026-10-29.json](qa/release-evidence-2026-10-29.json). Сырые логи и изображения находятся локально в `target/e2e`; они исключены из Git.
